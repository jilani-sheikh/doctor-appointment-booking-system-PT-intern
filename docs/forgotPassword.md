## Feature 1: Forgot password (credentials accounts)
- Sign-in page: "Forgot password?" link to /forgot-password (email form). /reset-password?token=... (new password + confirm).
- Schema: PasswordResetToken { id, userId (FK cascade), tokenHash String @unique, expiresAt, usedAt?, createdAt, index on userId }. Store only a SHA-256 hash of a crypto.randomBytes(32) token; never store the raw token. Add User.passwordChangedAt DateTime? (nullable).
- Request flow: always return the same generic message ("If an account exists for this email, we have sent a reset link") whether or not the email exists, with similar response time. Only create a token and email when the user exists AND has a passwordHash. For Google-only accounts send an email saying they signed up with Google and should use "Continue with Google" (no token). Expiry 30 minutes. Creating a new token invalidates earlier unused ones. Rate limit with existing patterns only (for example max 3 requests per email per hour and a per-IP guard using a small DB-backed counter or the existing maintenance/state approach); no new infrastructure.
- Reset flow: validate token (hash lookup, not expired, not used) in one conditional update (mark used atomically so it works once only), validate the new password with the same Zod rules as register (min 8, max 72, letter + number), hash with bcrypt cost 12, set passwordChangedAt = now, invalidate all other unused tokens for the user. Show friendly states: invalid, expired, already used, success with a link to /sign-in. Do not sign the user in automatically.
- Existing sessions: JWT cannot be revoked, so in getCurrentUser compare the token's issued-at with user.passwordChangedAt and treat older sessions as signed out. Keep the zero-credential invariant and the existing degrade-to-signed-out behaviour.
- Email: add a reset template (responsive HTML + plain text, escape content, no sensitive data, IST wording for the expiry, link built from APP_URL). Send through the existing email layer; the reset email is transactional and must send even if reminders are disabled. Failures must not reveal whether the account exists. README: Resend sandbox only delivers to the Resend account owner's address until a domain is verified.
- Tests: token hashing, expiry, single use, enumeration-safe responses, Google-only account path, password rules, session invalidation after reset, rate limit.

## Feature 2: Delete profile (patient and doctor)
- UI: in the navbar avatar menu, next to Sign out, add "Delete profile" (destructive styling) for PATIENT and DOCTOR only (never ADMIN; also refuse to delete the last ADMIN). It opens a confirmation dialog explaining exactly what will be deleted and what is retained, requires typing DELETE, and for credentials users also the current password. Google users confirm by typing DELETE plus their email. Also add the same action on the patient and doctor dashboard or profile page. Accessible dialog, pending state, Sonner toasts.
- Server action deleteAccountAction: Zod-validated, requireRole PATIENT/DOCTOR, userId from the session, rate limited, idempotent, errors with friendly messages (never raw Prisma errors).
- BLOCKERS (return a clear list and delete nothing):
  Patient: any appointment in CONFIRMED, CHECKED_IN or IN_CONSULTATION with a future or current slot; any PENDING_PAYMENT hold (offer to cancel the hold automatically); any refund in REQUESTED or PENDING. Tell the patient to cancel upcoming appointments first (so refunds are created) and try again after pending refunds finish.
  Doctor: any IN_CONSULTATION or CHECKED_IN appointment today; any refund in REQUESTED or PENDING. Upcoming CONFIRMED appointments are NOT a blocker for doctors: cancel them automatically through the existing doctor-cancel path (cancelledBy DOCTOR, 100% refund via the existing refund service, slot release, patient in-app + email notifications) BEFORE deleting, and report how many were cancelled.
- DELETION (after blockers pass), one reviewed algorithm per role. Decide the safest approach given the existing onDelete rules (Restrict on appointments/payments/refunds) and describe it in the plan:
  a) Permanently delete all personal and operational data: User.name/email/image/phone/passwordHash/accounts/sessions (Auth.js Account and Session rows), PasswordResetToken, notifications, notification_deliveries, waitlist entries, patient profile fields (DOB, gender, phone), doctor profile (specialization, qualification, bio, fee, settings), availability slots with no appointments, doctor time-off, wave rows with no remaining appointments, and any appointment/payment history that has NO payment or refund record (hard delete).
  b) Where payment or refund records exist (money history), keep only a minimal anonymized financial ledger: retain the Payment/Refund/Appointment rows needed for referential integrity and accounting, but scrub every personal field and detach identity (User row reduced to an anonymous tombstone: name "Deleted user", email "deleted+<id>@deleted.invalid", no image, no password, no accounts, role retained, a deletedAt timestamp). Remove reason text and any free-text. Document exactly what is retained and why (financial/legal record keeping) in the README and in the confirmation dialog.
  c) Add User.deletedAt DateTime? (nullable) and treat deleted users as nonexistent everywhere: sign-in, Google sign-in (a deleted user who signs in with Google again should create a fresh account, not resurrect the old one; make sure the unique email constraint is not violated by the tombstone), getCurrentUser returns null, doctor directory and slot listings exclude them, admin lists exclude them or show "Deleted user".
  d) Other people's views must not break: patients who had appointments with a deleted doctor see "Doctor no longer available" instead of a crash; doctors' history for a deleted patient shows "Deleted patient". Check every page that joins to doctor or patient (appointments views, receipts, queue, waves, admin payments, emails).
- Execute with short transactions or ordered array-form steps; the whole operation must be idempotent and safe to retry after a partial failure (use a state marker such as deletionRequestedAt, or conditional updates, so a retry finishes the job). Cancel pending outbox rows for the user. Free any held slots through the existing releaseSlot helper.
- After success: sign the user out (clear the session cookie via the existing signOut flow), redirect to / with a toast "Your profile has been deleted". Existing JWTs stop working because getCurrentUser reloads from the database.
- Send one final confirmation email BEFORE scrubbing the address (transactional, no personal details beyond "your Medrella profile was deleted"), best effort, never blocking deletion.
- Tests: blockers for each role, patient hard delete when no money history, anonymization when payments exist (no PII left in any column; list the columns checked), doctor deletion cancels upcoming appointments with refunds and notifies patients, idempotent retry, deleted user cannot sign in with the old password, Google re-signup creates a new account, other users' pages render with a deleted counterpart, ADMIN cannot be deleted, last admin protected.
